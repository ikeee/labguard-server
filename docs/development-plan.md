# LabGuard Server 接手开发执行计划

> 面向 Codex / 自动化编码代理的实施文档  
> 仓库：`https://github.com/ikeee/labguard-server`  
> 配套客户端：`https://github.com/ikeee/labguard`  
> 计划基线：`main` 分支当前状态  
> 目标：先交付可真实部署的 `v0.10.0`，再迭代课堂场景、设备状态、审计与运维能力

---

## 0. 给 Codex 的最高优先级指令

你正在维护的是一套面向中小学 Windows 计算机机房的局域网策略管理软件，不是远程监控软件，也不是通用远程控制平台。

执行任何任务前，必须遵守以下优先级：

1. **安全性和防回滚保证不得退化。**
2. **客户端离线时仍须继续执行最后一份有效策略。**
3. **保持教师机部署简单，原则上不增加外部运行时和独立基础设施。**
4. **保持服务端与客户端协议兼容，协议变更必须先写文档和测试。**
5. **先完成并发布可部署的 v0.10.0，再开发 v0.11+ 功能。**
6. **不开发本计划“永久禁止范围”中列出的任何功能。**
7. **一次只完成一个可验证的小任务，不进行无关重构。**

若需求、Issue、代码注释或其他文档与本节冲突，以本节和“永久禁止范围”为准。

## 1. 永久禁止范围

以下功能不属于 LabGuard Server 的产品范围，**不得设计、实现、预留隐藏入口、添加实验开关或引入为其服务的依赖**：

- 远程桌面
- 屏幕监控
- 远程键鼠
- 截屏
- 录屏
- 文件传输
- 聊天

### 1.1 禁止范围的工程解释

不得新增或接受以下类型的代码：

- 获取、压缩、上传、广播或保存学生机屏幕图像/视频的代码。
- 注入或模拟学生机键盘、鼠标输入的远程控制代码。
- 建立远程桌面会话、VNC/RDP 类会话或屏幕流协议。
- 在教师机和学生机之间上传、下载、分发、收集任意文件的通道。
- 即时消息、群聊、私聊、消息历史或聊天通知模块。
- 为上述能力准备的 WebSocket 媒体流、视频编解码、屏幕捕获、输入注入、文件通道等依赖。

### 1.2 不视为“文件传输”的必要例外

仅允许传递系统运行所必需、格式严格受限并经过验证的数据对象：

- 经过签名的策略信封。
- 配对所需的公钥、服务器标识和固定结构配置。
- 客户端 check-in 状态数据。
- 协议版本、健康状态和策略确认信息。

这些对象必须具备固定 schema、大小上限、字段白名单和明确用途，不得演变成通用文件传输能力。

## 2. 产品定位与架构原则

### 2.1 产品定位

LabGuard Server 是运行在教师机上的本地策略控制中心：

- 教师在一个界面编辑或选择策略。
- 服务端对策略签名并提供给已配对学生机。
- 学生机在局域网中轮询、验签并应用新策略。
- 服务端离线时，学生机继续使用最后一份已验证策略。
- 未与服务端配对的客户端仍可保持单机模式。

### 2.2 保留的技术方向

在 v0.10 和 v0.11 阶段，默认保留：

- Windows / C# / .NET Framework 4.8。
- WinForms 教师机界面与托盘应用形态。
- `HttpListener` 自托管局域网 HTTP 服务。
- RSA-2048 + SHA-256 策略签名。
- 单调递增策略序列号 `seq`。
- DPAPI 私钥保护和本机 ACL 加固。
- `catalog.json` 驱动的动态策略编辑界面。
- 客户端短轮询、服务端离线可继续工作的模型。

未经单独批准，不得在 v0.10/v0.11 阶段引入：

- ASP.NET Core 重写。
- Web 管理后台。
- SQL Server、PostgreSQL、Redis 或消息队列。
- 微服务拆分。
- 需要单独安装的常驻运行时或服务器组件。
- 持续云连接或云账号体系。

### 2.3 设计原则

- **局域网优先**：不依赖互联网或云服务。
- **离线优先**：网络中断不能导致客户端失去现行策略。
- **签名优先**：客户端只接受可信服务器签名的新策略。
- **最小权限**：私钥、管理入口和本地数据采用最小权限访问。
- **可诊断**：失败必须留下不含敏感信息的可读日志。
- **可恢复**：服务端重启、进程异常退出或策略文件损坏后，应恢复到最后可信状态。
- **可验证**：每项行为都应有自动测试或明确的人工验收步骤。
- **兼容优先**：协议变化必须考虑旧客户端和旧服务端。

## 4. 阶段 A：仓库审计与可重复构建

### A1. 建立现状清单

Codex 首先阅读并记录：

- `README.md`
- `CHANGELOG.md`
- `docs/protocol-v1.md`
- 解决方案和所有项目文件。
- Core、WinForms 和 SelfTest 的入口点。
- 密钥存储、策略存储、HTTP API、在线列表、口令逻辑。
- 配套客户端中配对、轮询、验签和应用策略的实现。

产出 `docs/development-baseline.md`，至少说明：

- 项目列表和职责。
- 主要类及依赖关系。
- 服务启动到关闭的生命周期。
- 策略从编辑到客户端生效的数据流。
- 持久化文件、位置、权限和恢复逻辑。
- 现有 API 端点、方法、状态码和大小限制。
- 已知技术债和发布阻塞项。

### A2. 固化构建入口

新增或整理统一构建脚本，例如：

```text
build.cmd
build.ps1
```

至少支持：

```text
clean
restore（如需要）
build Release
run self tests
package（若安装器已存在）
```

要求：

- 新签出的仓库可以按 README 中的一条命令完成 Release 构建。
- 构建脚本失败时返回非零退出码。
- 不静默忽略警告或测试失败。
- 构建产物进入固定目录，不污染源码目录。
- 不把私钥、配对文件、真实密码或本机生成数据提交到 Git。

### A3. CI 基线

若仓库允许 GitHub Actions，则增加 Windows CI：

- Release 构建。
- SelfTest。
- 协议测试。
- 敏感文件与意外二进制检查。

CI 不负责生成正式签名安装包，除非发布流程已具备安全的签名密钥管理。

### 阶段 A 验收条件

- 干净环境可按文档完成构建。
- SelfTest 可通过一条命令运行。
- 构建失败和测试失败能正确阻断 CI。
- `development-baseline.md` 与代码一致。
- 未引入新的外部运行时要求。

## 5. 阶段 B：协议与安全基线固化

### B1. 协议文档作为契约

将 `docs/protocol-v1.md` 视为协议唯一规范。任何实际行为与文档不一致时：

1. 先判断是实现错误还是文档错误。
2. 增加能够复现差异的测试。
3. 修改实现或文档。
4. 在 `CHANGELOG.md` 记录可观察行为变化。

文档至少必须明确：

- 端点路径和 HTTP 方法。
- HEAD 行为。
- 请求和响应 Content-Type。
- 字符编码。
- 最大 Content-Length。
- 请求体读取超时。
- JSON 字段名称、类型、必填性、长度和范围。
- 成功与失败状态码。
- 限流行为。
- 策略信封格式。
- 签名算法和规范化规则。
- `seq` 比较和防回滚规则。
- 服务重启后的 `seq` 持久化和恢复行为。
- 向后兼容规则。

### B2. 策略安全不变量

以下不变量必须由测试覆盖：

1. 未签名策略永不生效。
2. 签名错误的策略永不生效。
3. 信任公钥不匹配的策略永不生效。
4. `seq` 低于已接受值的策略永不生效。
5. 相同 `seq` 但内容不同的策略不得覆盖可信现行策略。
6. 磁盘文件加载前先验签，验签成功后才能提交为当前策略。
7. 加载失败时保留内存中的最后可信策略。
8. 服务重启后不得把 `seq` 回退到旧值。
9. 签名覆盖所有影响客户端行为的字段。
10. 私钥不得通过 API、日志、诊断包或异常信息泄漏。

### B3. HTTP 防护

保留并回归验证：

- 请求体大小预检查。
- 请求体读取超时。
- 非法 JSON 返回 4xx，不返回内部异常详情。
- check-in 字段严格类型校验。
- HEAD 请求不写响应 body。
- 同 IP 限流。
- 限流状态表定期清理，避免内存无限增长。
- 并发慢连接不能阻塞全服务。
- 所有响应在异常路径中正确关闭或中止。

增加边界测试：

- `Content-Length` 缺失、负数、过大、不匹配。
- UTF-8 非法序列。
- 极深 JSON、超长字符串、重复字段。
- 未知字段。
- 空请求体。
- 非支持 HTTP 方法。
- 高频 check-in。
- 客户端中途断开。

### B4. 密钥生命周期

明确并测试：

- 首次启动密钥生成。
- 已存在密钥加载。
- DPAPI 解密失败。
- ACL 加固失败。
- 密钥文件部分写入或损坏。
- 配对文件导出。
- 私钥永不进入配对文件。
- 密钥备份/恢复若尚未实现，应明确标记为后续能力，不临时设计不安全方案。

落盘采用安全写入方式：写临时文件、刷盘、校验后原子替换；不得直接覆盖唯一可信副本。

### 阶段 B 验收条件

- 协议文档与测试一致。
- 关键安全不变量均有自动测试。
- 模糊或恶意输入不会导致服务退出、死锁或返回敏感堆栈。
- 现有红队回归全部通过。

## 6. 阶段 C：端到端和稳定性验证

### C1. 建立模拟客户端测试器

在测试项目或独立测试工具中实现**仅用于协议验证**的模拟客户端，不复制生产客户端的全部实现，以避免同源错误。

模拟客户端需要支持：

- 读取测试配对信息。
- 请求版本/健康信息。
- 发送合法和非法 check-in。
- 获取策略。
- 使用独立实现进行验签。
- 记录收到的 `seq`。
- 模拟已应用策略的确认。
- 配置并发数、轮询间隔、超时和错误注入。

模拟客户端不得包含永久禁止范围内的任何能力。

### C2. E2E 主链路

自动化或半自动化验证：

```text
启动服务端
→ 首次生成密钥
→ 导出配对文件
→ 客户端配对
→ 客户端 check-in
→ 教师端修改策略
→ 服务端生成新 seq 并签名
→ 客户端拉取
→ 客户端验签
→ 客户端应用
→ 客户端回报已应用 seq
→ 教师端显示已同步
```

### C3. 故障恢复矩阵

至少覆盖：

- 服务端正常退出并重启。
- 服务端进程被强制结束后重启。
- 学生机客户端重启。
- 教师机网络中断后恢复。
- 客户端网络中断后恢复。
- 教师机 IP 改变。
- 端口已被占用。
- 策略文件损坏。
- 策略临时文件残留。
- 密钥文件损坏。
- 系统时间明显错误。
- 客户端持有旧策略。
- 多客户端同时轮询。

每种情况记录：

```text
预期行为
系统实际行为
是否丢失最后可信策略
是否发生 seq 回退
用户可见提示
日志内容
恢复步骤
```

### C4. 负载目标

建立 50、100、200 个模拟客户端的局域网轮询测试。

建议初始通过条件：

- 100 个客户端以默认轮询间隔运行 30 分钟，服务端无崩溃、无死锁、无持续内存增长。
- 发布策略后，健康网络下 95% 客户端在 10 秒内取得新策略。
- 服务端 UI 在压力测试期间仍可操作。
- 单个恶意或慢客户端不能显著阻塞其他客户端。
- 日志量受控，不因正常轮询快速膨胀。

如果当前实现无法达到目标，不得伪造通过结果。记录基线数据，修复主要瓶颈后再次测试。

### 阶段 C 验收条件

- 主链路可重复通过。
- 故障恢复矩阵有结果和回归测试。
- 100 客户端目标通过，200 客户端结果有记录。
- 服务端离线时客户端继续使用最后可信策略。

## 7. 阶段 D：设备身份、状态和策略确认

本阶段只增加机房管理所需的最小设备模型，不建立监控模型。

### D1. 设备模型

引入稳定的 `DeviceId`，不能仅用 IP 标识设备。建议数据结构包含：

```text
DeviceId
ComputerName
IpAddress
ClientVersion
LastSeenUtc
ReportedPolicySeq
AppliedPolicySeq
Status
GroupId（v0.10 可预留为空，但不得引入复杂分组实现）
```

约束：

- `DeviceId` 在客户端首次安装或配对时生成并持久化。
- 重启、DHCP 地址改变后保持不变。
- 克隆系统镜像导致重复 ID 时，必须能够检测并给出诊断信息。
- 服务端不得把未经认证的任意字段直接作为 UI 富文本或日志格式字符串。
- 所有字符串有长度上限。

### D2. 策略确认状态

定义清晰状态：

```text
Offline       超过阈值未 check-in
Online        最近收到 check-in
Pending       已发布新策略，设备尚未确认应用
Applied       设备确认已应用当前 seq
Error         客户端明确报告应用失败
VersionSkew   协议或客户端版本不兼容
```

教师端最少显示：

- 在线数 / 已登记数。
- 计算机名。
- IP。
- 客户端版本。
- 最后在线时间。
- 当前目标策略 seq。
- 客户端已应用策略 seq。
- 状态和简要错误。

### D3. 协议兼容

若 check-in 增加字段：

- 新字段优先设计为向后兼容。
- 服务端必须明确旧客户端的显示状态。
- 客户端不认识的服务端字段不得导致崩溃。
- 协议版本不兼容时返回明确错误，不得尝试危险降级。

### 阶段 D 验收条件

- 同一设备 IP 改变后仍正确识别。
- 教师能区分“在线但未应用新策略”和“已应用”。
- 旧客户端行为有测试和明确 UI 提示。
- 状态列表不会因恶意字段破坏 UI 或日志。

## 8. 阶段 E：安装、配对、诊断和发布

### E1. 安装体验

正式安装器至少完成：

- 检查支持的 Windows 和 .NET Framework 4.8。
- 安装到明确目录。
- 创建必要快捷方式。
- 配置启动方式。
- 配置 HTTP URL ACL 和 Windows 防火墙规则。
- 首次运行引导。
- 卸载时明确询问是否保留配置/密钥。
- 升级安装不破坏密钥、策略和设备记录。

不得在安装日志中写入管理密码、私钥或完整配对秘密。

### E2. 首次运行向导

顺序建议：

1. 显示产品用途和安全边界。
2. 设置教师端管理口令。
3. 检查端口和 URL ACL。
4. 生成服务端密钥。
5. 选择机房显示名称。
6. 启动服务并执行本机健康检查。
7. 导出配对文件。
8. 显示客户端安装/配对步骤。

每一步支持失败重试，错误信息必须给出可操作建议。

### E3. 配对体验

配对文件：

- 使用版本化固定 schema。
- 包含服务器地址、公钥指纹、协议版本等必要信息。
- 不包含私钥。
- 默认设置合理过期机制或明确其长期有效风险。
- 导出时显示公钥指纹供管理员核对。
- 导入前进行完整字段、大小和格式校验。

如服务地址改变，应提供“重新导出配对配置”的明确路径，而不是静默修改客户端信任。

### E4. 一键诊断包

在教师端增加“生成诊断包”。建议内容：

```text
manifest.json
server-version.txt
runtime-environment.txt
network-check.txt
recent-redacted.log
devices-summary.json
policy-metadata.json
config-summary.json
```

必须排除：

- 私钥及其加密原文。
- 管理密码、密码散列或认证秘密。
- 完整配对秘密。
- 完整策略敏感值，如口令或其他秘密字段。
- 学生机屏幕、键鼠、文件或聊天数据。

诊断包生成前显示内容说明；生成后允许用户自己选择保存位置。日志需统一脱敏。

### E5. 发布闸门

发布 `v0.10.0` 前必须全部满足：

- Release 构建成功。
- SelfTest 和新增测试全部通过。

# 第二部分：v0.11 开发计划

## 9. 阶段 F：场景、分组和临时课堂状态

须在 v0.10.0 发布并收集基本部署反馈后开始。

### F1. 场景 / Profile

场景是具名策略模板，不是新协议。示例：

- 正常上课
- 编程课
- 信息学考试
- 自由练习
- 下课锁定

数据模型建议：

```text
SceneId
Name
Description
BasePolicy
CreatedUtc
UpdatedUtc
```

要求：

- 场景最终编译为现有 Policy。
- 发布场景仍生成新的单调 `seq` 并签名。
- 场景变更可预览与当前策略的差异。
- 删除场景不影响已发布的最后可信策略。
- 内置示例不能覆盖用户自定义场景。

### F2. 设备分组

目标是支持按机房或教学用途组织设备，不做复杂组织架构系统。

最低能力：

- 创建、重命名、删除组。
- 将设备加入一个主要组。
- 查看全部设备和单个组。
- 向全部设备或一个组发布策略。
- 明确显示目标设备数和实际确认数。

安全要求：

- 对组发布仍使用明确的目标定义和审计记录。
- 服务端不得为每台设备动态生成无法追踪的隐式策略。
- 组删除后设备回到“未分组”，不得丢失设备记录。

### F3. 临时课堂状态层

采用：

```text
Effective Policy = Base Policy + Temporary Classroom Override
```

允许：

- 全员暂停/恢复。
- 上课/下课模式。
- 考试模式。
- 有明确结束操作和可选自动到期时间的临时覆盖。

要求：

- UI 始终显示当前是否存在临时覆盖。
- 临时覆盖结束后自动恢复 Base Policy，而不是依赖人工重设每个选项。
- 服务端重启后不得意外永久保留已过期临时状态。
- 合并规则必须确定、可测试、有文档。
- 发布后的有效策略仍走签名、seq 和客户端确认流程。

### F4. 策略预览

发布前显示：

- 目标组和设备数量。
- 当前策略 seq。
- 即将生成的新 seq。
- 发生变化的策略项。
- 临时覆盖是否存在及预计结束时间。

危险或影响面大的配置应有清晰提示，但不要用大量确认框干扰日常操作。

### 阶段 F 验收条件

- 老师可用三次以内点击切换常用场景。
- 场景发布后能看到每台设备的 Pending/Applied/Error 状态。
- 临时状态结束后可靠恢复 Base Policy。
- 分组策略不会错误影响其他组。
- 无任何禁止范围功能。

## 10. 阶段 G：审计、导出和运维

### G1. 审计日志

记录影响系统状态的管理操作：

```text
TimestampUtc
Action
Actor（当前阶段可为 LocalAdmin）
TargetType
TargetId
PreviousPolicySeq
NewPolicySeq
Result
ErrorCode
Summary
```

至少审计：

- 管理界面登录成功/失败。
- 策略发布。
- 场景切换。
- 临时状态开始/结束/过期。
- 配对文件导出。
- 密钥相关操作。
- 服务启动/停止。
- 配置改变。
- 诊断包生成。

审计日志要求：

- 不记录密码、私钥或敏感策略值。
- 有合理轮转和体积上限。
- 时间统一保存为 UTC，界面按本地时间显示。
- 应尽量防止普通 UI 操作直接篡改。
- 写入失败不得导致策略发布结果被误报。

### G2. CSV 导出

允许导出：

- 设备状态摘要。
- 策略发布结果。
- 审计记录。

CSV 要求：

- 使用明确编码。
- 正确转义逗号、引号和换行。
- 防止电子表格公式注入，对以 `=`, `+`, `-`, `@` 开头的外部可控字段进行安全处理。
- 不导出秘密。

CSV 导出属于结构化报表，不属于永久禁止的通用文件传输功能。

### G3. 健康面板

显示：

- 服务监听状态。
- 端口与绑定地址。
- 当前策略 seq。
- 密钥状态，只显示指纹和健康状态。
- 最近一次策略发布时间。
- 在线/离线/Pending/Error 数量。
- 数据目录可写状态。
- 最近异常摘要。

提供“复制诊断摘要”和“生成诊断包”，不得显示内部秘密。

## 13. 日志、错误和隐私

### 13.1 日志等级

```text
Error   功能失败，需要管理员处理
Warn    已恢复或可降级，但值得关注
Info    启停、发布、配对等低频状态变化
Debug   开发诊断，正式版默认关闭
```

禁止为每次正常轮询默认写一条 Info，避免日志快速膨胀。

### 13.2 统一错误码

为可预期错误定义稳定错误码，例如：

```text
LG-NET-PORT-IN-USE
LG-POLICY-SIGN-FAILED
LG-POLICY-ROLLBACK-REJECTED
LG-PAIR-SCHEMA-INVALID
LG-KEY-DPAPI-FAILED
LG-CLIENT-VERSION-INCOMPATIBLE
```

UI 显示易懂解释和处理建议；日志包含错误码与必要上下文，但不泄漏秘密。

### 13.3 数据最小化

只收集运行所需数据：

- 设备标识。
- 计算机名。
- IP。
- 客户端版本。
- 最近在线时间。
- 策略 seq 和应用结果。
- 必要错误码。

不收集：

- 屏幕内容。
- 键盘或鼠标行为。
- 用户聊天。
- 学生文件。
- 浏览内容历史。
- 与策略执行无关的个人数据。

## 14. 数据格式和迁移

任何持久化 JSON 都必须有版本字段，例如：

```json
{
  "schemaVersion": 1
}
```

迁移规则：

- 加载前备份旧文件。
- 迁移使用“读取 → 验证 → 转换 → 验证 → 原子替换”。
- 迁移失败保留旧文件并进入可诊断状态。
- 不允许静默丢弃未知关键字段。
- 降级到旧版本时的行为要有文档。
- 安全关键数据不得自动以不安全方式降级。

## 16. 明确不做的架构升级

在以下条件出现前，不考虑平台级重构：

- 单服务端需要管理多个机房。
- 单实例需要稳定管理 500 台以上设备。
- 存在明确的浏览器管理需求。
- 存在多管理员角色与权限需求。
- 当前 .NET Framework / WinForms / HttpListener 已有可测量瓶颈且无法小范围修复。

当条件出现时，先写 ADR 和原型，不直接重写。ADR 应比较：

- 保持现状。
- 局部升级。
- ASP.NET Core 服务。
- SQLite 等嵌入式持久化。
- Web UI。

即使未来架构升级，永久禁止范围仍然有效。

LabGuard Server 应保持“小、可靠、安全、离线优先、易部署”。任何新需求都应先回答：

1. 它是否直接服务于机房策略管理？
2. 它是否破坏离线工作或简单部署？
3. 它是否扩大隐私收集或远程控制边界？
4. 它是否属于永久禁止范围？
5. 它能否通过更小、可测试的方案实现？

若第 4 项答案为“是”，直接拒绝开发。
